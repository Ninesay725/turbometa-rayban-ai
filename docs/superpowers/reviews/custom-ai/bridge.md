# Custom AI bridge additions

Base: `android-v2` / `f470179`. Scope: bridge Kotlin, notification bridge service/screen, dedicated bridge AI resource files, bridge tests, this report. Parent owns Gradle and assistant integration; no Gradle, commits, push, credential reads, or network AI calls in this work.

## Integration contracts

- `BridgeSettings.aiNotificationsEnabled: Boolean = false` and `aiNotificationPackages: Set<String> = emptySet()`; main-confined `BridgePreferences.setAiNotificationsEnabled(Boolean)` and `setAiNotificationPackages(Set<String>)`. Independent of `wechatEnabled`; parent assistant settings owns configuration UI. Package setters use the existing exact-package validation convention (trim, discard invalid entries, deduplicate).
- `BridgeSettings.aiConsentRevision: Long = 0L` is RAM-only. Each actual toggle/normalized package-set change increments it; no-op edits leave it unchanged. Compare `Triple(aiNotificationsEnabled, aiNotificationPackages, aiConsentRevision)` so a rapid off/on or remove/re-add cannot restore the old consent identity. No revision preference key is written, and a reconstructed preferences instance starts at zero.
- Pure `AssistantNotification(notificationKey, packageName, title, text, timestamp)`; RAM only, newest 20 distinct notification keys, title capped at 256 UTF-16 units and text at 2,000. No persisted notification contents or logging.
- `NotificationBridgeRuntime.assistantNotifications: StateFlow<List<AssistantNotification>>` and main-confined `notificationsForAssistant(packageName: String? = null): List<AssistantNotification>`. Explicit reads recheck toggle, exact package allowlist, exact listener permission, and connected service. Unauthorized reads throw safe descriptive `IllegalStateException` without notification contents or causes.
- `NotificationBridgeRuntime.assistantAccessEpoch: StateFlow<Long>` starts at zero and is RAM-only. It advances on observed system-access loss, lock/noninteractive transition or explicit listener screen-off/locked broadcast, disconnect/retirement, and connected-listener replacement, even with an empty cache. It also advances when a formerly readable cached entry is invalidated by privacy ranking or a hidden/unreadable posted replacement. Read it as an opaque invalidation generation, not an exact event count. Readable updates, ordinary removals, and visible summary deduplication do not advance it.
- Main-confined, **non-suspending** `NotificationBridgeRuntime.controlForAssistant(action: String, packageName: String? = null): String`. Exact lowercase actions: `play`, `pause`, `next`, `previous`; governed by existing `musicEnabled` / `mediaPackages`, listener permission and connection. Explicit package selects only that package; omitted package uses playing-first selection. Fresh active sessions/capabilities at invocation; no fallback to another package for unavailable/unsupported explicit targets. Generic success means the platform accepted the command dispatch, not confirmation of playback.
- `AssistantMusicController` is the dedicated service interface; it does not change `MusicController`. These methods execute only on explicit parent invocation. Settings/defaults never initiate AI network traffic. An `ACTION_PLAY_PAUSE` capability alone does not authorize explicit play/pause; the corresponding `ACTION_PLAY`/`ACTION_PAUSE` bit is required.

## Retention and privacy

- The service checks opt-in and exact selected package before touching notification extras. The assistant path is independent of the WeChat display path. It does not replay already-active notifications on enable/reconnect.
- One current snapshot per notification key, sorted newest first by notification post time. Same-key replacement removes old content before parsing, including missing/unreadable/summary/redacted replacements. Removal, disable, settings narrowing, listener disconnection/replacement and permission loss discard relevant data. Synchronous setter eviction prevents a quick off/on or remove/re-add from being lost through StateFlow conflation.
- Secret visibility is always rejected. Private/unknown visibility is rejected while keyguard-locked or the screen is noninteractive. User/device-policy ranking visibility can only narrow access. A posted notification without ranking is treated as secret. Android ranking updates remove newly hidden snapshots without rereading contents and advance the epoch for formerly readable entries. A key absent from an update's ranking map is pruned without advancing the epoch, because ordinary removal also produces that absence. Ranking-read exceptions still fail closed as secret.
- Screen-off clears the cache; reads also check lock state before returning data. Exact component notification access is checked through `NotificationManager.isNotificationListenerAccessGranted`, with a permission-settings observer for revocation cleanup. Observers/receiver are removed on service retirement, including partial-registration failure.
- Parser handles public title/big-text/text, then the latest nonblank current MessagingStyle message among its last 20 entries. It ignores historical messages, public-version fallbacks, intents, remote views and attachments. Unreadable platform data and platform command exceptions do not propagate content-bearing messages or causes.
- StateFlow is an in-process current-state view. Parent requests must call `notificationsForAssistant` at invocation time and must discard any already-copied data/cancel network work when authorization changes; the bridge cannot revoke a copy already handed to another component.
- Platform privacy APIs verified against [Android Notification](https://developer.android.com/reference/android/app/Notification), [notification ranking visibility](https://developer.android.com/reference/android/service/notification/NotificationListenerService.Ranking#getLockscreenVisibilityOverride()), and [exact listener access](https://developer.android.com/reference/android/app/NotificationManager#isNotificationListenerAccessGranted(android.content.ComponentName)). The requested Meta `llms.txt?full=true` reference was fetched but returned a login page; no DAT API changes were required here.

## Consent-generation follow-up (2026-09-11)

Implemented the requested cross-boundary invalidation contract. The old toggle/package comparison could return to the same value before a collector resumed, even though the bridge had already cleared its inbox. The new `aiConsentRevision` prevents that equality from being restored; existing positional constructors remain compatible because the defaulted field is appended. It is incremented only by actual assistant consent changes and never persisted. English/Chinese UI resources and UI/VM files were not edited by this worker.

The new `assistantAccessEpoch` also lets already-copied work detect external authorization changes. Runtime reads/settings reconciliation observe access and lock state; the service's existing permission observer retires the listener on revocation; screen-off/locked events invalidate even an empty cache; detach advances the epoch before platform-controller cleanup. Repeated reads of unchanged locked/denied state do not continuously advance it, and restoring permission/connection never resets it. A first connection is not itself an invalidation; replacing a connected listener is.

Parent/UI wiring: snapshot both the consent Triple and `assistantAccessEpoch.value` for notification work, observe changes to both, and recheck both at tool/result boundaries. On invalidation, cancel notification requests/speech and clear derived private output. Comparing only the Boolean/package pair or only the current connection Boolean is insufficient. The latest parent source already includes the consent Triple; epoch wiring remains parent-owned. These tokens signal cancellation; they cannot retract data already sent to an external provider.

Regression tests added: an Android preferences test exercises rapid consent round trips, normalized no-ops, no writes for initial no-op edits, and revision reset on reconstruction while checking exact stored keys. Pure inbox tests exercise permission/disconnect round trips with an empty cache, read-detected lock clearing, stable denied reads, explicit lock/connected-listener replacement, and ordinary notification changes without epoch churn. ## Intermediate instrumentation timeout diagnosis (2026-09-11)

Parent's `intermediate-instrumentation.txt` records 11/12 passing; the real posted-notification bridge fixture times out after 10 seconds. Its coroutine stack contains neither a test line nor a stage, so it cannot establish which of the seven waits failed. That installed APK predates the consent/access-generation follow-up and does not validate those newer changes.

Source inspection found a concrete fixture defect affecting the original fourth-delivery wait: the same key changes from group summary back to a child of the same group. In [AOSP NotificationManagerService](https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/android12-release/services/core/java/com/android/server/notification/NotificationManagerService.java), enqueue adds the child before `handleGroupedNotificationLocked`; losing the summary cancels matching children in both posted and enqueued lists. This can remove the new child before listener delivery. It is a source-supported failure mechanism, not proof of the historical failing stage.

The test now checks removal before the final summary replacement, preserving all coverage without that summary-to-child transition. Every wait has a distinct assertion label: listener connection, first delivery, delivery after off/on, delivery after allowlist round trip, removal eviction, delivery after removal, and summary replacement eviction. Timeout diagnostics report connection/access/lock/consent flags, cache count, RAM generations, posting permission/channel importance, and presence/summary status of only the test-owned notification. No notification text, keys, extras, platform exception messages, or causes are printed.

No production bridge changes were needed for this diagnosis. Existing current-source removal, synchronous consent eviction, exact access/allowlist checks, and conservative ranking/lock filtering remain intact. Parent should rebuild/reinstall and rerun `com.smartview.glassai.bridge.AssistantNotificationBridgeInstrumentedTest`; a remaining failure will now identify its boundary. ## Privacy-eviction epoch correction (2026-09-11)

Confirmed the review finding in the actual service/runtime path: a secret ranking deleted its entry through ordinary removal, leaving the epoch unchanged. Posted replacement erased the prior entry before parsing, so an unreadable result also lost the evidence needed to invalidate copied work.

The inbox now remembers prior readability across erase-before-parse and advances the existing epoch if the replacement is rejected or throws a guarded runtime exception. Ranking privacy eviction removes only the affected cached entry and advances the same epoch. Repeated rejection of an already absent key and first-time hidden notifications do not advance it. Unrelated readable cache entries remain available. Readable updates, ordinary removals, absent-ranking pruning, and visible group-summary deduplication preserve the parent's retention policy without epoch churn. A summary that is itself privacy-hidden still follows the privacy path.

Parent/UI contract is unchanged: observe and snapshot `assistantAccessEpoch` alongside the consent Triple, then cancel notification requests/speech and clear derived output when either changes. The existing VM factory already supplies this flow. No UI, assistant, preferences, media-control, or resource changes were made for this correction.

Regressions: four pure inbox tests cover privacy-only eviction, no repeated/unknown-key invalidations, erase-before-parse, readable replacement/summary behavior, and sanitized read failure. The Android parser regression now asserts epoch changes for malformed and redacted same-key replacements. The posted-notification test asserts readable-update/removal/summary epoch stability and real unreadable-replacement invalidation; it also injects visibility values through the runtime route used by the service to cover allowed, absent, secret, and repeated-secret ranking cases. This ranking regression does not change OS policy; it uses test-only reflection to obtain the already-connected publisher, without adding a production test accessor.
