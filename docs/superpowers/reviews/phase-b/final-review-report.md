## Strengths

- **The protocol port is faithful and better-fenced than the original.** I re-checked every item of research §8.6 against `OpenClawNodeService.kt` and `OpenClawDeviceIdentity.kt`: envelopes, the `connect` frame (`:351-374`), the v3 signature string (`OpenClawDeviceIdentity.kt:80-92`, `deviceId = sha256hex(rawPubKey)`, base64url no padding, `platform` used in both JSON and signature), `chat.send` (`:497-513`), both invoke shapes with `params|paramsjson` and `timeoutMs|timeoutms` (`:461-472`), `node.invoke.result` with `payloadjson` as a string (`:515-530`), `tick{ts}`, `NOT_PAIRED`, `UNSUPPORTED`, and the four payload shapes in the router. The four iOS quirks the research told us not to port (every `ok:true` restarts the tick, un-encoded token, double-counted reconnects, `openclaw_enabled`) are all gone, and each deviation is a deliberate improvement: hello matched by the pending `connect` id, socket-identity fencing in `handleDisconnect` (`:283`), `Reconnecting(attempt)` as its own state so Home auto-connect cannot defeat the 2/4/8/16/30 s sequence (verified on device, Task 9 item 3), `wss://`, blank token deletes. The RFC 8032 known-answer test pins Tink's Ed25519 output, and the instrumented handshake over cleartext `ws://` proves the NSC and the real listener end to end.
- **The frame-source design is the right shape and mostly right in the details.** `latestFrame` published by whichever borrower decodes (`WearablesViewModel.kt:561-566`, `RTMPStreamingViewModel.kt:383-387`), cleared at every camera/session teardown (`GlassesSessionManager.kt:362, 403, 450`), the `liveFrame()` gate (`GlassesFrameProvider.kt:219-224`) that refuses a frame unless `currentCameraOwner != null && sessionState == STARTED` (pinned by `staleFrameAfterStopCameraIsNotServed` and `frameIsNotServedWhileSessionIsPaused`), the fail-closed foreground gate, `awaitActiveDevice` so the first command after process start does not lie, and the router touching the manager only through `withContext(Dispatchers.Main.immediate)` for the capturer (`:118`). Task 9 item 11 shows the live path working during Live Stream in <1 s with no capturer round trip.
- **B2 was done properly, not cosmetically.** `HttpClients.websocket` removes the per-instance `OkHttpClient` leak (thread count 4→5→3 across cycles, Task 9 item 17); weak-ref listeners plus `close()`+`cancel()` in both cloud services; `RTMPStreamingService` now has a real lock discipline (`stopLock → encoderLock`, documented at `:99-104`, never inverted, the output loop calls `stopStreaming()` only after leaving `encoderLock`), a dedicated `rtmp-disconnect` executor so socket I/O never runs on Main, generation fencing on both start and stop, encoder release on `initEncoder` failure, no busy-spin on a null encoder (`canStartOutputLoop`), the `Error` state preserved through `stopStreaming()` at both layers, the stream key encrypted and never rendered or logged (`RtmpUrlSplitter.split(rtmpUrl).first` in every log line), and a one-shot `rtmp_url` migration with instrumented coverage.
- **Phase A's carry-overs were actually landed.** All four Phase A Importants (camera `stop()` on device-initiated stop, HEIC decode off Main, RTMP error swallowing, VM testability) and the MUST-FIX D1 (MockDeviceKit rehydration, `MockDeviceKitViewModel.kt:63-65`) are in; `FrameConversions` is the single YUV pipeline (the three copies are gone, `QuickVisionService` delegates), the four toast blocks are gone and `WearablesErrorToast` sits above the `NavHost` with `errorEvents` as the one-shot channel and `errorMessage` kept as state (Quick Vision reads `StreamState.Error.message` directly now), `CAMERA` moved to the debug manifest, `clearStopping` is non-self-referential, `takeIf { it in devices }` in the adapter, `Theme.kt` deprecated writes removed, `initializeSDK` renamed.
- **Testing is real, not decorative.** 147 JVM tests drive the protocol through OkHttp's `MockWebServer` with a scripted gateway (backoff, force-connect mid-backoff, NOT_PAIRED socket replacement, tick lifecycle, max-retries, invalid host, IPv6/token encoding), the provider through fakes with mutation-checked gates, the chat ViewModel through a fake recognizer and a fake SCO route, and Fun-ASR through a full run-task/audio/finish-task session. The 20 instrumented tests add the real SDK paths (PAUSED on captouch — which corrected a wrong assumption in the brief — fold, migration on real `EncryptedSharedPreferences`, PCM capture, encode clamps). String parity is exact (451/451). Task 9's manual pass found the two real defects below instead of hiding them.
- **Process discipline held.** Every controller ruling is recorded with a reason, every fix round has a scoped re-review, the KDoc in the hot spots explains the *why* (e.g. `GlassesFrameProvider.kt:71-82`, `RTMPStreamingService.kt:110-118`), and the docs are accurate: no lens-rendering claim ("Display glasses work as camera devices"), foreground-only `camera.snap`, `wss://`, the unverified Singapore Fun-ASR endpoint called out in README item 6.

## Issues

### Critical (Must Fix)

**C1. Snap & Send never returns a frame while the chat is open, and every gateway `camera.snap` answers `NO_FRAME` while the chat is foregrounded (Task 9 D-4).**
`GlassesFrameProvider.kt:168` gates the capturer fallback on `manager.ownerCount > 0`; `OpenClawViewModel.kt:182-188` `enterScreen()` calls `sessionManager().acquire(OWNER)` (spec §3 decision 1) and never publishes; `GlassesSessionManager.kt:148-149` counts every owner alike.
*Root cause:* the Task 4 ruling ("fallback only when `ownerCount == 0`") and the Task 6 design ("entering the chat acquires the session") are mutually inconsistent, and the Task 6 brief's fake `GlassesFrameProvider` made `OpenClawViewModelTest` blind to it. `SessionFrameProviderTest.fallbackIsSkippedWhileAnotherOwnerHoldsAClaim` (`:186-195`) pins the wrong behaviour: it acquires `"B"` with no camera intent and asserts `NoFrame`. This is a plan fault, not an implementer slip.
*Which fix:* not "drop the chat's claim" (violates decision 1, makes every snap pay the 12 s session start, and Phase C needs the session alive for the OpenClaw Display card); not "have the chat publish" (it would have to stream continuously — battery and Bluetooth bandwidth for nothing; iOS starts and stops the stream per snap). The correct and minimal fix is to **distinguish camera claims from session-only claims in the manager**, which is exactly the distinction Phase C (Display-card owners) and Phase E (the notification bridge) will need anyway:
- `GlassesSessionManager`: `fun acquire(owner: String, forCamera: Boolean = false)`; keep a `cameraIntents: LinkedHashSet<String>` maintained on Main and a `@Volatile private var cameraClaimCount`; `release()` removes from both; expose `val hasCameraClaim: Boolean get() = cameraClaimCount > 0 || cameraOwner != null` (volatile reads only — `ownerCount` is a `LinkedHashSet.size` read off Main today at `GlassesFrameProvider.kt:168`, which the new flag also fixes).
- Camera borrowers pass `forCamera = true`: `WearablesViewModel.kt:361`, `RTMPStreamingViewModel.kt:213`, `GlassesPhotoCapturer.kt:95`. The chat (`OpenClawViewModel.kt:185`) keeps the default.
- `SessionFrameProvider.snapshot()` `:168`: `if (manager.hasCameraClaim)` instead of `ownerCount > 0`; update the KDoc at `:71-76`.
- Tests: change `fallbackIsSkippedWhileAnotherOwnerHoldsAClaim` to `acquire("B", forCamera = true)`; add `sessionOnlyClaimDoesNotBlockTheCapturer` (acquire `"OpenClawChat"` without intent → `captureCalls == 1`, `Ok`); add `cameraIntentFollowsAcquireAndRelease` to `GlassesSessionManagerTest`; extend `openClawFrameProviderSnapsThroughTheSharedSession` (instrumented) with a session-only `acquire("OpenClawChat")` held across the snapshot and assert the claim survives (`ownerCount == 1` after, session still `STARTED`).

**C2. RTMP hangs in "Connecting" after a failed attempt and Stop from that state ANRs (Task 9 D-6/D-7).**
`RTMPStreamingViewModel.kt:139-141`: on service `Error` the VM only sets `UIState.Error` — the borrowed camera keeps streaming behind the error card (Task 9 measured 48-56 % CPU for the preview while the card is up), the session claim is kept, and `videoWidth` stays at 480. `clearError()` → Idle, then Start → `startCameraStream()` (`:204-207`) does `stopCamera(OWNER)` and an immediate same-session `addCamera`; frames arrive but `handleVideoFrame` (`:350`) never re-enters the `videoWidth == 0` branch, so `connectRtmp()` is never called; `armFirstFrameTimeout` (`:305`) is a no-op for the same reason. `videoWidth/videoHeight` are only reset in the VM's own `stopStreaming()` (`:419-421`), which the error path never calls.
The ANR on Stop is `sessionManager.stopCamera(OWNER)` → SDK `Camera.stop()` (and `release` → `session.stop()`) on Main taking >5 s. It only reproduces after the same-session camera hand-off that D-6 forces, which matches the Phase A Task 9 SDK finding (`VideoDecoder.activateDecoder()` vs `Camera.stop()` race); a healthy Connecting → Stop does not ANR (Task 9 item 19 and the late-callback check).
*Fix:* (1) add `private fun teardownCamera()` (cancel jobs, `camera = null`, `stopCamera`, `release`, reset `videoWidth/videoHeight/frameTimestampBase`, null `_previewFrame`/`_cameraState`) and call it from the `StreamingState.Error` branch, keeping `UIState.Error` — an RTMP failure ends the attempt, the camera must not stay borrowed behind an error card (it also blocks Quick Vision/OpenClaw with `CameraBusy`); (2) reset `videoWidth/videoHeight/frameTimestampBase` at the top of `startStreaming()` (`:190-202`) and track "first frame of this attempt" with an explicit flag set in `handleVideoFrame` rather than `videoWidth`; (3) with (1) in place, `startCameraStream()` never holds a camera at Start, so `:207`'s `stopCamera(OWNER)` becomes a defensive no-op — keep it but add a `check`/log if it was not a no-op; (4) re-run the D-6 sequence + Stop on the emulator; if `camera.stop()` still blocks, move the SDK `stop()` calls inside the manager onto the existing async stop path (Phase A recommendation 1) — bookkeeping stays synchronous. Test: a JVM test cannot build the VM (it holds a real `RTMPStreamingService`); add the seam described in I6 or at minimum an instrumented "start → connection failure → Start again reaches `connectRtmp`" case using an unreachable `rtmp://` endpoint (Task 9 already has the recipe).

### Important (Should Fix)

**I1. Concurrent snaps share one capturer owner and can release each other's camera and session.** `SessionFrameProvider.create()` is called twice (`OpenClawIntegration.kt:27` for the gateway and `OpenClawViewModel.kt:62` for the chat), both capturers use `OWNER = "OpenClawSnap"`, and `GlassesPhotoCapturer.capture()` (`:95-102`) does `acquire(owner)` / `release(owner)` on a *set*. A gateway `node.invoke camera.snap` landing while the user taps Snap & Send (or two invokes in flight — `dispatchInvoke` launches each on its own coroutine, `OpenClawNodeService.kt:480`) means the first `release("OpenClawSnap")` drops the shared claim while the other capture is mid-stream: `release` → `stopCamera` (if it holds it) → `stopSession()` when the set is empty. *Fix:* one provider instance per process (`OpenClawIntegration` exposes `frameProvider(app)` lazily; the VM's public constructor uses it) **and** a single-flight `Mutex` in `SessionFrameProvider` around the permission-check + capture path (companion-level so the guarantee does not depend on instance sharing); inside the lock re-check `liveFrame()` before capturing. Test: two concurrent `snapshot()` calls against a fake capture that suspends → exactly one capture at a time, both `Ok`.

**I2. Device monitoring is now started before the Bluetooth grant and cannot be restarted.** `OpenClawIntegration.kt:24` starts `GlassesSessionManager.startMonitoring()` from `Application.onCreate` (Task 4 fix round 1). `startMonitoring()` (`GlassesSessionManager.kt:172-191`) guards on `deviceJob != null`; the flow's `.catch { Log.e }` (`:179`) *completes* the flow on error, `runCatching` sees success, `deviceJob` stays a completed non-null Job, and every later `startMonitoring()` is a permanent no-op. `WearablesViewModel.startMonitoring()` (`:177`) does not call the manager's `startMonitoring()` at all, so the post-grant path in `MainActivity.startWearablesMonitoring()` (`:131-138`) never re-arms it. Whether the DAT device flows throw or silently never emit when collected before `BLUETOOTH_CONNECT` is granted is **unverified**: Phase A Task 10 item 15 verified initialize-in-Application with monitoring started *after* the grant, Task 9 ran everything with `pm grant` up front, and MockDeviceKit needs no Bluetooth. If the SDK needs the permission at collection time, a fresh install shows "no device" for the whole process life. *Fix:* (a) `job.invokeOnCompletion { if (deviceJob === job) deviceJob = null }` so a dead observer is restartable; (b) `WearablesViewModel.startMonitoring()` calls `sessionManager.startMonitoring()` first (idempotent when alive, restart when dead); (c) `OpenClawIntegration.install()` starts monitoring only if `BLUETOOTH_CONNECT` is already granted — before the grant there cannot be a device, so `camera.list` answering `[]` is correct; (d) device check on the owner's phone: fresh install → deny → grant → device card appears without a restart.

**I3. A `connect` rejected with any error other than `NOT_PAIRED` leaves the app in "Connecting…" forever; `OpenClawErrorReason.Transport` is dead code.** `OpenClawNodeService.kt:379-393` only reacts to `NOT_PAIRED`; a gateway that answers `ok:false` (e.g. an auth/protocol error) and keeps the socket open never reaches `handleDisconnect`, the tick never starts, and nothing retries. `Transport` (`OpenClawModels.kt:42`) is never constructed although `OpenClawStatus.kt:23` localizes it. *Fix:* when `id == pendingConnectId && !ok && code != NOT_PAIRED`: `shouldReconnect = false`, close the socket (1000), state `Error(Transport("$code: $message"))`; test `connectRejectedWithAnotherCodeIsReportedAsTransportError`. While there, also wrap the identity resolution in `sendConnect` (`:339`, Keystore/`EncryptedSharedPreferences` I/O on the OkHttp reader thread) in `runCatching` → `Error(Transport(...))` instead of letting a throw become five reconnects and "Connection failed after 5 retries".

**I4. The chat can leave the phone stuck in `MODE_IN_COMMUNICATION`.** `OpenClawViewModel.switchAudioSource(BLUETOOTH_MIC)` (`:417-426`) arms SCO on chip selection via `holdSco()` (`:375-379`); `BluetoothAudioManager.startBluetoothSco()` (`:195-209`) sets `audioManager.mode = MODE_IN_COMMUNICATION` immediately, but `stopBluetoothSco()` (`:214-229`) returns early unless `isBluetoothScoOn`, which is only set by the `SCO_AUDIO_STATE_CONNECTED` broadcast. If SCO never comes up (headset connected but SCO fails, `SCO_AUDIO_STATE_ERROR`, or the user taps the chip and leaves within the 3 s window), `releaseSco()`/`cleanup()` never reset the mode: media stays muted and the volume rocker controls call volume until another feature resets it. Latent in Live AI too, but the chat's arm-on-selection makes it likely. *Fix (in the manager, benefits Live AI):* track `scoRequested`; in `stopBluetoothSco()` always run `isBluetoothScoOn = false; stopBluetoothSco(); mode = MODE_NORMAL` when `scoRequested || isBluetoothScoOn`. Consider arming SCO on the first mic press instead of on chip selection (the bounded wait already exists) — that is the ledger's "SCO held while the chip is selected" item and can wait for Phase D.

**I5. The LAN gateway client has no keepalive detection.** `lanHttpClient()` (`OpenClawNodeService.kt:110-114`) sets no `pingInterval`; the app-level `tick` is fire-and-forget (`:406-415`) and nothing checks for a reply. When the phone roams off Wi-Fi the socket is half-open, `send()` keeps succeeding into the kernel buffer, and the UI shows Connected for minutes until TCP gives up; `node.invoke` requests are silently lost in that window. iOS has the same gap, but OkHttp fixes it for free: `.pingInterval(20, TimeUnit.SECONDS)` fails the socket when a pong is missing → `onFailure` → the existing backoff. One line plus an assertion in `lanHttpClientBypassesProxiesAndNeverTimesOutReads`.

**I6. Test gaps I would block on.** (a) The D-4 test pins the wrong behaviour (see C1). (b) `RTMPStreamingService` has effectively no coverage (`RTMPStreamingServiceTest` tests a 1-line pure function): the generation fencing, `stopLock` single-disconnect, and the Error-preservation-through-stop are all "verified by inspection" across two fix rounds — extract the `ConnectCheckerRtmp` handling and the state transitions into a `RtmpConnectionState` class that takes `encoder: Any?`/`client: Any?` seams so those three invariants get JVM tests. (c) No test for the RTMP Error → Start-again sequence (C2). (d) `OpenClawViewModelTest` uses a fake `GlassesFrameProvider`; add one test that wires the *real* `SessionFrameProvider` over the fake manager with the chat's claim held, so C1 cannot regress from the VM side. (e) No JVM test for the concurrent-snap case (I1).

### Minor (Nice to Have)

Keep a `userDisconnected` flag in the service that suppresses auto-connect until the next explicit `connect(force = true)` or process restart.
2. **No recovery from `Error(MaxRetries)` except Settings → Connect** (ledger T6). Let Home's auto-connect also fire from `Error(MaxRetries)` on a fresh Home visit (bounded by navigation, not a loop).

5. **Dead / unreferenced:** `R.string.version` (`strings.xml:193`, both locales) is unreferenced since the About row moved to `settings_version`. `rtmp_disconnected` (`:522`) is referenced by `RTMPStreamingViewModel.kt:147` but reachable only if rtmp 2.2.6 ever calls `onDisconnectRtmp` for a live drop, which it does not — keep it (a library upgrade will make it live), add a one-line comment. `Transport` — fixed by I3.
6. **Codec teardown on the caller's thread.** `RTMPStreamingService.stopStreaming()` (`:502-510`) runs `MediaCodec.stop()/release()` under the locks on whichever thread calls it — Main on a user Stop (`RTMPStreamingScreen.kt:291`). Not an ANR, but tens of ms of jank; hand the codec teardown to the same executor as the disconnect (order preserved) or have the VM call it from `viewModelScope.launch(Dispatchers.IO)`.
7. **Fun-ASR callbacks mutate ViewModel fields off Main.** `onError` (`OpenClawViewModel.kt:334-337`) runs on an OkHttp thread and calls `stopListening()` (`:355-362`), which writes `listenJob`/`asr` that Main also writes. Hop: `viewModelScope.launch { ... }` inside the three callbacks. Related: `FunASRService.stop()` before `task-started` sends `finish-task` first; a server `task-failed` in reply is not suppressed by `stopping` (`:285-295`) and surfaces as "Speech recognition failed" after a quick tap-stop.
8. **`dispatchInvoke` swallows `CancellationException`** (`OpenClawNodeService.kt:485`; ledger T3) — `if (e is CancellationException) throw e` before the generic catch; and document the `tickJob == null` invariant on `startConnection()`.
9. **Phase A Minors still open that Phase C/E will trip over:** no debug main-thread guard on the manager's mutators (Phase A #18) — Display `onClick` callbacks and `NotificationListenerService` callbacks arrive off Main, add `if (BuildConfig.DEBUG) check(Looper.getMainLooper() == Looper.myLooper())` now; `DisplayAttacher` KDoc (`DatGateway.kt:100-115`) still does not say `maybeAttach` fires on every STARTED including PAUSED→STARTED resume (Task 9 confirmed the *session* goes PAUSED on captouch) and that `activeDevice` may arrive after STARTED (Phase A #10); `getInstance(context)` ignores `context` (Phase A #8).
10. **Session-only owners cannot get a session across a STOPPING window.** `acquire()` (`GlassesSessionManager.kt:199-208`) refuses to create while `stoppingSession != null` and only camera borrowers call `ensureSessionStarted`. Leaving Live AI and immediately opening the chat leaves the chat with a claim and no session until a snap forces one. Harmless for OpenClaw, but Phase C's Display-card owners (music/WeChat) will need an `acquireAndStart(owner)` that awaits the previous STOPPED and creates — design it into the manager before Phase C rather than in each caller.
11. **Cleartext is permitted app-wide** (`network_security_config.xml:7-12`). Unavoidable for a user-typed LAN IP (NSC cannot whitelist address ranges), and every cloud endpoint is `https/wss`; add a sentence to the README security note so nobody "fixes" it later.
12. **`resetForTests()` does not reset `deviceJob`, `_activeDevice` or `_lastSessionError`** (ledger T1/T4) — a test that calls `startMonitoring → resetForTests → startMonitoring` short-circuits.
13. **`OpenClawSettingsScreen` reads `EncryptedSharedPreferences` during first composition** (`:71-74`, `APIKeyManager` construction ≈ 100 ms on Main) — same pre-existing pattern as every other screen; move to a `LaunchedEffect` when the screen is next touched.

## Recommendations

1. **Treat "camera claim vs session claim" as the manager's public contract from here on.** Phase C's Display-card owners (Live AI/Quick Vision/LeanEat cards while their features run, music/WeChat cards) and Phase E's `NotificationBridgeService` are all session-only owners; with step 1 above they keep the session alive without ever blocking `camera.snap`, and the capturer's `CameraBusy` path stays the only conflict. Also add the `acquireAndStart(owner)` suspend for session-only owners (Minor 10) and the debug main-thread guard (Minor 9) before Phase C code arrives from Display `onClick` threads.
2. **Do not touch the SDK stop path yet, but instrument it.** If step 8's D-7 re-run still blocks on `camera.stop()`, the defensive move is Phase A recommendation 1 (SDK `stop()` calls on the async stop path inside the manager, bookkeeping synchronous), not per-caller workarounds. Either way, log `camera.stop()`/`session.stop()` wall time in debug builds so the Phase C hardware pass produces numbers.
3. **Stub gateway fidelity.** `android/tools/openclaw-stub-gateway/stub.js` is a good smoke tool but it validates neither the Ed25519 signature nor the `signedAt` window, never sends a non-`NOT_PAIRED` error, and only checks the query token. Before the owner's first real-gateway session, add `--verify-signature` (tweetnacl) and `--reject <CODE>` switches so I3's path and the signature string are exercised outside the JVM tests; record the first real `openclaw devices approve` round trip in the Phase C report.
4. **Testing strategy going forward.** Extract the RTMP connection state machine behind seams (I6b); keep `am instrument` as the runner on this host; when the owner's phone is available, the three N/A checklist items (Quick Vision inline error, Fun-ASR Beijing and Singapore) plus the two verification items added here (I2d, D-7 re-run) are the Phase B closing list.
5. **Plan-level observations.** The plan let Task 4 and Task 6 define the two halves of one invariant independently, and gave Task 6 a fake provider — the FAIL was structurally guaranteed. Future plans should name cross-task invariants explicitly ("the chat's claim must not block the capturer") and require at least one test that composes the real classes across the seam. The same applies to `install()` starting monitoring at `Application.onCreate` (a Task 4 ruling) without a "fresh install, permission granted later" check in Task 9's brief.
